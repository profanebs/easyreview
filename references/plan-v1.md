# plan/v1 模板与规则（速查）

> **语言约定**：中文文档用中文节名与字段名（下表），英文文档用英文；解析器两套都认
> （`## T1:` ＝ `## 任务 T1:` ＝ `## Task T1:`，`**这是啥**:` ＝ `**What**:`，`# 接着咋整` ＝ `# 决策点` ＝ `# Decisions Needed`；
> 旧的 `做什么 / 为什么 / 会怎么坏 / 怎么改` 拼法仍可解析）。
> 交付给墨然的默认用中文。

## 模板（中文版）

```md
---
schema: plan/v1
title: <标题>
status: needs_review
risk: low | medium | high
review_level: L0 | L1 | L2
traceability: true
decision_required: true | false
doc_id: review-YYYY-MM-DD-<slug>
---

# 摘要
- 一句话结论
- 建议动作
- 最大风险

# 这是啥
这是什么，改了什么，影响范围。

# 因为啥
为什么这样做，备选方案，权衡。

# 咋想滴
- 我替你假设了什么（没问过你的）
- 请核查；不对就驳回

# 要干啥 / 不干啥
- 建议左右对照表（目标 vs 非目标），比单列「非目标」好扫

# 这波整了啥

## T1: <任务标题>

**这是啥**: ...

**因为啥**: ...

**会咋坏**: 最可能失效的场景、外部依赖断了会怎样

**咋修复**: 坏了怎么修／退路是什么

**变更**:
- 文件: <path>
- 类型: feature | fix | refactor | docs

**验收**:
- [ ] 验收项 1
- [ ] 验收项 2

**证据**:
- 命令: `<命令>`
- 结果: <输出摘要>
- 状态: verified | unverified | failed

**决策**:
- [ ] 需要人拍板的点（能给选项就用 :::question）

# 接着咋整
- [ ] 文档级决策点

# 未验证
- 还没验证的项
```

## 英文版（同构，字段名换英文）

`# TL;DR / # What / # Why / # Assumptions / # Non-goals / # Tasks / ## T1: / **What**: / **Why**: / **Failure**: / **Fix**: / **Changes**: / **Acceptance**: / **Proof**: / **Decisions Needed**: / # Decisions Needed / # Unverified`

## 决策点：用 :::question 写「选项 + 推荐」（不是纯文本）

审阅页会在右栏「批注」面板的**「接着咋整」区**把 `:::question` 块渲染成**可点的选项芯片**（推荐项标「荐」），点一下就是一条答案，回流时进
"Answers to your questions"。纯文本的 `- [ ]` 决策点没有这个交互——**能给出选项的决策一律用 :::question**。

```
:::question
技能命名定哪个？

- [ ] easyreview — 直白，和项目目录一致
- [ ] deslop — 强调"去屎山"，容易被误读成只做清理

Recommended: easyreview — 直白，和项目目录一致
:::
```

- 单选 `:::question`、多选 `:::question-multi`、自由文本 `:::question-text`；
- `- [ ] label — 说明`：破折号后半句是给审阅者的补充；
- `Recommended:` 指向某个选项即标「荐」；指不到选项就是"建议的自由文本"；
- 真正没法给选项时才退回纯文本 `- [ ]`（它会作为兜底列进「接着咋整」同一区）。

## 审阅者的四问（审阅页侧栏会逐条展示）

审阅页对每个任务问五件事，缺一条就会在侧栏挂一个「缺 N 问」的警告：

| 四问 | 来自字段 | 审阅者想看什么 |
|---|---|---|
| 这是啥 | `**这是啥**`（旧拼法 `**做什么**`） | 到底做了什么，边界在哪 |
| 因为啥 | `**因为啥**`（旧拼法 `**为什么**`） | 为什么这么做，考虑过什么替代 |
| 会咋坏 | `**会咋坏**`（旧拼法 `**会怎么坏**`） | 最可能怎么失效、依赖断了怎么办 |
| 咋修复 | `**咋修复**`（旧拼法 `**怎么改**`） | 坏了怎么修、退路是什么 |
| 证据 | `**证据**` | 命令 + 输出 + 状态；没跑就写 unverified |

**别用"不适用"糊弄**：真没风险就写"纯文档改动，无运行时风险"——写清楚为什么没有，比留空强。

## 硬规则

1. front matter 必填五项：schema / title / status / risk / review_level。
2. TL;DR 恰好 3 条。
3. 每个 task：Acceptance + Proof 缺一不可；**Failure / Fix 建议必写**（L0 除外），缺了审阅页会明确提示。
4. Proof 状态只允许 verified / unverified / failed；没跑的证据写 unverified / 未开始。
5. `decision_required: true` 时必须有 Decisions Needed 内容。
6. 无 task ID 的代码改动不合法——先更新 plan 再加 task。
7. 决策点尽量给「选项 + 推荐」（+30~80 token），审阅者回答成本更低。
8. 交付前自查两条：**我替你假设了什么**（`# 咋想滴`，可选节）；**这次不做什么**（`# 要干啥 / 不干啥` 的右列，可选节）——两列对照表，比单列更好扫。
9. **字段分段**：每个 `**字段**:` 独占一段（段间留空行）。四问卡与验收行按段落边界跳转，字段挤在同一段里会跳不准、也不好看。

## 分层建议

- L0：不写 plan、不渲染（一句话能说清的改动）。
- L1：裁剪版（TL;DR + What/Why + 1~2 个 task）。
- L2：完整版（含 Failure Modes、Unverified、决策点）。
